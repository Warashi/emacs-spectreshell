** TODO M-3: 同一バッファでの並行ジョブで端末領域が交錯する
対象: =spectreshell-eshell.el= (=--attach= / gather advice)

=spectreshell--current= / =spectreshell-eshell--process= が単一スロット
のため、=command &= 実行中に次のコマンドを打つと後発 attach が先発を
上書きし、双方が「marker〜point-max」を自領域とみなして削除・上書きし
合う。先発の detach は後発ジョブ実行中でも無条件に semi-char モードを
解除する。

端末領域を複数持つ設計変更 (領域終端マーカーの導入、per-process の
領域管理) が必要で、docs/design.org の「最後のパイプラインステージ
のみ」簡略化の見直しを含む。別途設計してから対応する。

実端末での再現手順 (2026-09-05, tmux 80x24):

1. =sh -c 'i=0; while [ $i -lt 15 ]; do echo "BG-$i"; sleep 0.4; i=$((i+1)); done' &=
2. 背景ジョブの出力が続いている間に前景コマンドを打って RET

打った文字はコマンドラインに入らず背景ジョブの pty へ送られ、pty の
echo で端末領域に文字列として現れるだけで、コマンドは実行されない
(RET も =eshell-send-input= に届かない)。=spectreshell-eshell-mode=
を無効にした素の eshell では同じ操作で前景コマンドが普通に実行される
ので、spectreshell 固有の後退。

背景ジョブが終われば状態は元に戻り (=spectreshell--current= も
semi-char モードも解除される)、以後のコマンドは実行できる。失われるのは
実行中に打った入力だけ。

=test/spectreshell-eshell-test.el= の
=spectreshell-eshell-test-background-job-leaves-command-line-usable=
が =:expected-result :failed= で固定してある。

** TODO L-22: 子プロセスから見える端末幅が COLUMNS と ioctl で 1 桁ずれる
対象: =spectreshell-eshell.el= (=--terminal-size= / =--window-size-change=)

=spectreshell-eshell--terminal-size= は桁数に
=window-max-chars-per-line= を使う。この値は tty フレームでは折り返しの
継続グリフのぶん最終桁が予約されるため =window-body-width= より
1 小さい。一方 eshell 本体 (=esh-var.el=) は子プロセスへ export する
=COLUMNS= を =window-body-width= で定義しているので、子から見た幅が
環境変数では 80、=TIOCGWINSZ= では 79 になる。

80x24 の実端末で確認した実測値:

#+begin_example
$ sh -c "echo COLUMNS=$COLUMNS; stty size < /dev/tty"
COLUMNS=80
21 79
#+end_example

=tput cols= は COLUMNS を優先するため 80 を返す。79 桁の行は 1 行に
収まるが 80 桁ちょうどの行は 2 行に折り返るので、COLUMNS を信じて
描くアプリは 1 行ごとに 1 行余分に消費する。ncurses は setupterm で
COLUMNS を ioctl より優先するため、全画面を使う TUI が該当する。
リサイズ後も同じずれが残る (100 桁にすると COLUMNS=100 / ioctl 99)。

対象は COLUMNS を読むアプリに限る。COLUMNS を読まないコマンド
(=git log --oneline= など) の出力が 80 桁で折り返すのは、tty の Emacs
ウィンドウが元々 79 桁ぶんしか文字を表示できない (80 桁目が継続グリフ用)
ことによるもので、この課題とは別。実測では 80 桁ちょうどの subject を
持つコミット 30 件を出しても欠落は無く、各行が 79 桁と 1 桁に割れて
1 画面に見えるコミットが半減するだけだった。

=test/spectreshell-eshell-test.el= の
=spectreshell-eshell-test-terminal-cols-match-eshell-columns= が
=:expected-result :failed= で穴を固定してある。

どちらに揃えるかは設計判断が要る。=window-body-width= に合わせると
継続グリフの桁と端末の最終桁が衝突する恐れがあり、逆に eshell の
COLUMNS 定義を spectreshell 側で 79 に上書きする案もある。GUI
フレームでは両者が一致する可能性があり、tty 固有かどうかも未確認。

** DONE L-2: キーマップの穴 (backtab / 修飾付き TAB・RET・DEL)
対象: =spectreshell.el= (semi-char keymap, =spectreshell--event-to-key=)

=backtab= (GUI の S-TAB)、=C-<tab>= / =M-RET= / =C-<backspace>= 等が
未束縛で Emacs 側コマンドに流れていた。=spectreshell--event-to-key= も
ascii 特殊キー判定が raw イベント完全一致だったため、=M-RET= が
=return= + alt にならなかった。

判定を「Emacs の修飾ビットだけを落とした文字」で行うようにし
(=spectreshell--event-char=)、=backtab= は =tab= + shift への読み替え表
(=spectreshell--aliased-key-symbols=) で扱う。束縛側は修飾付き特殊キーの
ループに tab / return / backspace / escape / backtab を追加した
(900d340・234e9b9・cd38ac4、=test/spectreshell-key-table-test.el= の
=M-RET= / =C-<backspace>= / =<backtab>= 行)。

** DONE L-19: シフト付き英字が小文字で送られる
対象: =spectreshell.el= (=spectreshell--event-to-key=)

=event-basic-type= が =?A= を =?a= に落として shift を修飾子側へ移す
ため、KEY が =("a" shift)= になり PTY には =a= が出ていた。EVENT が
BASIC の upcase 形そのものなら生の EVENT を KEY に使うようにして対応
(7a3a954、=test/spectreshell-key-table-test.el= の =A= / =Z= 行)。

meta 併用の大文字 (=M-A=) は meta ビットにより =characterp= の外へ出る
ため当初は対象外だったが、修飾ビットを落とした文字で判定するよう改めて
対応した (900d340・3a9fe0d、=M-<大文字>= の束縛追加を含む。同じ表の
=M-A= 行)。

** DONE L-20: C-M-<letter> がキーマップに無く送られない
対象: =spectreshell.el= (semi-char keymap)

キーマップは =C-<letter>= と =M-<letter>= を個別に束縛しているだけで
=C-M-<letter>= の組が無く、Emacs 側のコマンドに流れていた。
=--event-to-key= は =?\C-\M-a= を =("a" ctrl alt)= に正規化できていた
ので、a-z 全字の束縛を足して対応 (a031601、
=test/spectreshell-key-table-test.el= の =C-M-a= 行)。docs/design.org の例外は =C-c= / =C-x= プレフィックス・
=M-x=・=C-y= で、どれも =C-M-= 版とは別イベントのため除外は設けていない。

** DONE L-21: パイプ最終段で pty の termios が正されない
対象: =spectreshell-eshell.el= (=--wrap-command-for-pty=)

pty を Emacs が開いた直後の既定は =-onlcr= で、そのままだと LF が改行
にならず出力が階段状になる。これを避ける =stty= ラッパは当初 =term.el=
の =term-exec-1= と同じく標準入力に対して =stty= していたが、
spectreshell が pty 化するのは出力側だけ (=--force-pty-output=)
であり、パイプの最終段では標準入力が eshell の plain pipe になる。=stty= が ENOTTY で失敗し (stderr は =null-device=
送りで無言)、=ls | cat= のような日常的なパイプの出力がすべて階段状に
崩れていた。

=stty= の対象を子プロセスの制御端末 =/dev/tty= (= Emacs が開いた pty)
に変えて対応 (0f650de、=test/spectreshell-eshell-test.el= の
=spectreshell-eshell-test-piped-output-lines-start-at-column-zero=)。

** TODO B-1: zig 自前 x86_64 バックエンドの .so segfault が直ったら use_llvm を外す
対象: =build.zig= (=addLibrary= の =.use_llvm = true=)

zig 0.15.2 の自前 x86_64 バックエンド (Debug ビルドの既定) が生成した
libspectreshell.so は、Emacs から dlopen して最初の =smp_allocator=
確保に入ると =SmpAllocator.getCpuCount= 内の未初期化レジスタ参照
(=movq (%r9), %rax= で r9=0) により segfault する。qemu-x86_64 +
lldb で特定し、LLVM バックエンド強制 (=.use_llvm = true=) で回避中。
zig を更新した際は x86_64 の Debug ビルドで ERT が通るか確認し、
直っていれば =use_llvm= 指定を外して Debug ビルドを高速化する。

** TODO B-2: ghostty が SDKROOT を直接使うようになったら xcode-shim を外す
対象: =nix/emacs-spectreshell.nix= (=xcodeShim=)

macOS の Nix サンドボックスには Xcode がなく、ghostty の
=pkg/apple-sdk= がビルドグラフ構築時に呼ぶ zig の
=LibCInstallation.findNative= が =xcode-select --print-path= と
=xcrun --sdk <名前> --show-sdk-path= の実行に失敗して
=DarwinSdkNotFound= panic になる (aarch64-darwin の =nix flake check=
が全滅)。$SDKROOT (apple-sdk setup hook が設定) を返すだけの
xcode-select / xcrun シムを darwin のみ nativeBuildInputs に足して
回避中。

xcbuild (xcode-select / xcrun 同梱) では代替できないことを CI で確認
済み: macosx SDK は $DEVELOPER_DIR から解決できるが、ghostty の
build.zig は darwin ターゲットだと XCFramework 用に iOS / iOS
Simulator 向けグラフも無条件に構築し (=GhosttyXCFramework.init=)、
そこで要求される iphoneos SDK は CLT 由来の Nix apple-sdk に存在
しない。シムは --sdk の値を無視して macOS SDK を返すのでここも通る
(iOS 向けステップはグラフに乗るだけで実行されない)。

ghostty の pkg/apple-sdk (または zig std) が xcrun を介さず SDKROOT
環境変数を直接尊重するようになったらシムを削除する。

対象: =spectreshell.el= (=spectreshell--decorate-row=)

=just bench= の 40 区間/行 (50x200) で、1 フレーム 11.6 ms のうち

** DONE P-1: point の強制移動でスクロールバック閲覧が実質不能
対象: =spectreshell.el= (=spectreshell--move-point=)

毎 update で point と全ウィンドウの window-point をカーソル位置へ移す
ため、emacs モードで履歴閲覧中も出力のたびに引き戻されていた。

term.el と同様に、更新前の point が前回のカーソル位置だったときだけ
追従させるようにして解決した。判定は再描画の前に済ませ、バッファの
point と各ウィンドウの window-point で個別に行う。semi-char モード中は
常に追従する (d8699ff)。

** DONE P-2: font-lock 有効時に dirty 行スキップ最適化が無効化される
対象: =spectreshell.el= (=spectreshell--apply-dirty=)

=fontified= プロパティにより =equal-including-properties= が常に不一致
になり、全 dirty 行を毎回書き換えていた。

比較対象をバッファのテキストから「モジュールが最後に送ってきた生の
=(TEXT . SPANS)=」に変えて解決した。他モードが後から付けたプロパティに
左右されず、装飾を組み立てる前に短絡できる (9aa4f2a)。

** TODO P-3: Zig ホットパスの intern / funcall 回数

キーワードシンボルを feed ごとに =intern= し直している。

** TODO P-4: XTGETTCAP が無応答 (残り)
対象: =src/handler.zig=

DECRQM (b0294c9) と kitty keyboard query (5ed6133) は ghostty 本体の
=src/termio/stream_handler.zig= と同じ応答を返すようにした。DECRQM は
既知モードに 1 / 2、未知モードに 0 を返す (ghostty 同様 3 / 4 は使わ
ない)。なお ANSI 形式の DECRQM (=CSI Ps $ p=) は ghostty 1.3.1 の
=stream.zig= が intermediates 2 個の場合しか dispatch しないため、ハン
ドラまで届かない (=src/core.zig= に現状を固定するテストあり)。

XTGETTCAP は未対応。応答値はビルドで同梱する terminfo (ghostty の
=src/terminfo/main.zig= の xterm-ghostty) と一致させる必要があり、
ghostty 本体は =terminfo.ghostty.xtgettcapMap()= を comptime で引いて
いる。この定義は =ghostty-vt= モジュールが再エクスポートしていないた
め、=build.zig= で本体モジュールに =ghostty-terminfo= (terminfo 生成
exe 用に作っているものと同じ =src/terminfo/main.zig=) を =addImport=
しないと handler から参照できない。手書きの表は同梱
terminfo との乖離を招くので採らない。=build.zig= を触れる時に、
=dcs_hook= / =dcs_put= / =dcs_unhook= を横取りして
=ghostty_vt.dcs.Handler= に流し、=.xtgettcap= の各キーを map で引いて
返す (未知キーは ghostty 同様に無応答) 形で対応する。

** DONE P-5: --pad-rows の O(n^2) と modification hooks
対象: =spectreshell.el=

ループ 1 周ごとに =count-lines= で全域を数え直していた。必要行数を一度
計算して一括 insert にし、dirty 行の位置決めも先頭から数え直さず前の行

=inhibit-modification-hooks= の束縛は見送っている (他モードのフック
互換性とのトレードオフで、計測上の支配項でもない)。

* レビューで検証済みと確認した点 (記録)

- モジュール境界の関数名・アリティ・plist 形式は Elisp 宣言と
  =registerAll= で完全一致。
- user-ptr の finalizer を型タグに使う検証、=--release= の二重解放
  安全化 (set_user_ptr null で GC finalizer を no-op 化) は正しい。
- ペーストのエスケープ注入は ghostty =paste.encode= が ESC・C-c 等の
  危険バイトを bracketed paste の有無によらず空白置換しており安全。
  =core.zig= が mutable コピーを渡すのはこの sanitize を働かせる正しい
  呼び方。
- 依存ピン留め (build.zig.zon hash + flake.lock + コミット済み
  build.zig.zon.nix)、ライセンス同梱、README / マニュアルの記述精度
  (TERM フォールバック・キーバインド・検出パス) はコードと一致。

** TODO M-14: 高速な出力の確定テキストがまとまって欠落する
対象: =src/core.zig= / 同梱の ghostty-vt (=PageList=)

子が出した行が、確定テキストにもモジュールが返す =:scrolled-off= にも
現れずに消える。3 つの条件で観測した。

1. 幅の広いウィンドウでの素の出力 (F-super-2)。tmux ペインを W x 24 に
   リサイズして =sh -c 'seq 1 100000'= を実行するだけで、リサイズも
   ウィンドウ操作も出力中には一切していない。

   #+begin_example
   幅 (桁)  gap 数  欠落行数
        80       0         0
       100       0         0
       120       1       389
       160     168     48888
       220     168     38584
   #+end_example

   220 桁では 425 行の欠落が約 680 行間隔で周期的に並ぶ。160 桁は
   計 3 回試して 3 回とも欠落した (168 gap / 48888 行、167 gap /
   48597 行、167 gap / 48597 行。回によって gap が 1 つ前後するので
   pty の読み取り境界に依存する部分がある)。120 桁は 1 回のみ。ワイド
   ディスプレイで eshell を全幅で使うと、ログやビルド出力の途中が
   まとまって消える。

2. 出力中に幅を変えずに高さだけ増やすリサイズ (F-concurrency-4 /
   F-concurrency-19)。=sh -c 'seq 1 200000'= の実行中に
   =(split-window)= → =(delete-other-windows)= を 1 回行うと、5/5 回とも
   きっかり 5 か所で 9・7・5・3・1 行、計 25 行が消える。gap の間隔は
   毎回 585 行。tmux のペインリサイズでも同じで、80x24 → 80x12 →
   80x24 で 30 行、80x15 → 80x40 → 80x24 で 135 行。縮小のみ、および
   幅も同時に変えた場合 (60x15 → 120x40) は 0。素の eshell でも 0。
   ただし 60x12 → 80x24 は幅が変わっても高さのみの場合と同じ 30 行が
   欠けており (F-concurrency-19 の表)、「幅が変われば起きない」は
   無条件の規則ではない。
   欠けた番号はバッファのどこにも文字列として存在せず、行の結合でも
   折り返しの見落としでもなくテキストが失われている。

3. 1 回の feed が大きい場合 (F-module-2)。21x80 の端末に 1200 行を
   1 回の =spectreshell-feed= で流すと、確定テキストの先頭が 577 行目に
   なり先頭 576 行が消える。消えるのは常に先頭側で 576 の倍数。
   cols=200 では 464 行、cols=400 では 580 行が単位。連番の「穴」では
   ないので、gap を数えるだけの計測では見落とす。

いずれもモジュールが返す =:scrolled-off= の時点で同じだけ欠けており、
バッファを一切作らない batch (=spectreshell--feed= / =--resize= を直接
呼ぶだけ) でも再現する (F-module-1 / F-module-2)。したがって
=spectreshell.el= の描画・確定処理ではなく Zig モジュール側の欠陥。
Debug ビルドと nix の Release ビルドで結果は完全に一致し、同じ入力なら
欠落位置まで一致する (決定的)。

Linux の pty 経由では 1 回の feed は 4095 バイトを超えない (F-super-1、
=spectreshell-feed= に advice を付けて 169 回ぶん実測)。Emacs 31.1 の
=read-process-output-max= の既定は 65536 だが、pty master からの read が
4095 で切れるため。80 桁で 3 の経路を踏まないのはこれによるもので、
幅が広いと 1 ページに入る行数が減って閾値が下がる、というのが 1 と 3 の

推測 (H-module-1、コード読解のみ): =src/core.zig= の =buildUpdate= は

しか持てず、cols=80 のページ容量は実測から 576 行と見られる。gap の
間隔 585 行と 1 回の feed で落ちる単位 576 行の差 9 が、gap ごとに欠落
行数が減る公差 9 と一致する点も同じ筋で説明できる。ページ容量を直接
確かめる API がモジュールに無いため未検証。上記 2 の反例

** TODO M-16: ghostty-vt の log が Emacs の stderr (= tty) へ直書きされ画面を壊す
対象: =src/main.zig= (=std_options= / =logFn= の未指定)

=emacs -nw= の stderr は端末そのものなので、モジュールが =std.log= で
書いた行が Emacs の画面表現を通らずに tty へ出る。Emacs の増分再描画は
これを知らないので、以後の画面が恒久的に壊れる。この文字列は
=*Messages*= にも =*Warnings*= にも無い。

最も派手な例 (F-apps-9、4/4 回): 起動直後の eshell で =vim -u NONE= →
=:q!= とすると、バッファは 3 行で完全に正常なのに画面 21 行が vim の
起動画面の残骸で埋まる。時間が経っても直らず、以後のコマンド出力は
残骸の上に重ね書きされる。=(redraw-display)= を呼べば一発で直る。
Emacs の stderr をファイルへ逃がして同じ手順を踏むと残骸は完全に消え、
警告文だけがファイルに残る (3/3 回) ので因果は確定している。警告を
出さない nvim では起きない。

契機のバイト列は実測で確定した (F-stderr-5)。=script= で捕った vim の
出力に含まれる =CSI 22;1t= と =CSI 23;1t= で、vim 自身に吐かせると
=t_Si= (save icon) と =t_Ri= (restore icon) に一致する。ghostty は
=CSI 22/23 t= のうちタイトル (=;2=) だけを実装するため、アイコン側の
2 つが必ず警告になる。vim は起動時と終了時に送るので、使うたびに 2 件
出る。他の契機も総当たりで数えた (F-stderr-4): DECSET / DECRST は
1996/2031 が未実装モードの警告、=CSI n t= は 48 中 44、C0 の 0x03 /
0x04 / 0x06、sixel などの DCS 4 種、OSC 1 と rxvt 拡張。行頭に来た
ゼロ幅・結合文字 (U+200B / U+FEFF / U+0301 単独) でも出る
(F-geometry-2)。

一次情報 (F-stderr-1): =src/*.zig= に =std_options= も =logFn= も無い
(=grep= で 0 件) ので、zig 既定の =std.log.defaultLog= がそのまま fd 2
へ書く。ReleaseSafe の既定 log level は info なので、
=info(terminal_dcs): unknown DCS hook: …= のような info の行も同じ経路で
画面に出る。ビルドされている ghostty には重複抑止が無く、vim を 3 回
使えば警告はちょうど 6 件出る。

実運用で踏むのは事実上 vim だけで、git / ls --color / less / htop /
fzf / infocmp / 全角の折り返し / SGR 全パラメータ / OSC の主要番号 /
terminfo の描画系 capability はいずれも警告ゼロだった (F-stderr-2 /
F-stderr-6。terminfo で警告が出るのは端末がアプリへ送る側のキー
capability だけで、 =cup= =csr= =ich= などの描画系は引数を与えた
正しい形なら全部無警告)。
ただし警告が 1 件でも出れば画面は壊れ、出なければ壊れない (同一手順で
画面の非空行数が 3 行 ↔ 20 行、F-stderr-3)。残骸の大きさは「警告が
書かれた後に Emacs がその領域を描き直すか」で決まるので揺れる。

前回の探索的テストの F-2 (画面にだけ前の内容が残る) と見え方は同じだが、
F-2 の元手順 (=seq 1 100= → =cd= → =git log --oneline=) では警告が 1 件も
出ず (F-stderr-2)、その手順自体も 0/23 回で再現していない
(F-concurrency-5)。同一だとは断定しない。

** DONE L-23: macOS でパイプ最終段の stty が /dev/tty を開けず出力が壊れる
対象: =spectreshell-eshell.el= (=--wrap-command-for-pty=)

L-21 で =stty= の対象にした =/dev/tty= が macOS では開けず、CI
(macos-26) の ERT 2 件が落ちていた。バッファに出ていたもの:

#+begin_example
/nix/store/.../coreutils-9.11/bin/cat: /dev/tty: Device not configured
                    a
                     b
                      c
#+end_example

エラー行が混入し (=2>/dev/null= を付けているのに漏れる)、=stty= が走ら
ないので出力が階段状になる。エラーが =cat:= 始まりなのは
=sh -c SCRIPT PROGRAM ARGS= で =$0= が PROGRAM になるためで、=cat= 自身
ではなくシェルがリダイレクトの失敗を報告している。

=stty= の対象を fd 1 の複製に変え、stderr の捨て場をリダイレクト列の
先頭へ移して対応 (ccefbbe、テストは 361779a の
=test/spectreshell-eshell-test.el= の
=spectreshell-eshell-test-wrap-command-sanitizes-pty-without-ctty=)。
このテストは =setsid= を要するため、nix の checkPhase と devShell に
util-linux を足した (90bd4aa・4f41e5a)。
pty 化するのは出力側だけである以上、fd 1 はラッパが動く状況では必ず
pty であり、制御端末の有無に依存しない。

一次情報として確認した点:

- Emacs 31.1 の =callproc.c= =emacs_spawn= は子で =setsid()= した後、
  =pty_in= が真のときだけ =ioctl (std_in, TIOCSCTTY, 0)= を呼ぶ。
  eshell (=esh-proc.el=) はパイプ最終段に =(pipe . nil)= を渡し、
  =--force-pty-output= はその cdr だけを =pty= にするので
  =(pipe . pty)= すなわち =pty_in= は偽になる。
- 制御端末を得るもう一つの経路である「pty を =O_NOCTTY= 無しで開き直
  す」ブロックは =DONT_REOPEN_PTY= で囲まれており、=configure.ac= は
  darwin と各 BSD でこれを定義する。理由として「既に TIOCSCTTY したの
  で制御端末になっている」と書かれているが、その前提は =pty_in= が真の
  ときしか成り立たない。
- Linux ではこの再 open が効く。=drivers/tty/tty_jobctrl.c= の
  =tty_open_proc_set_tty= が、セッションリーダが制御端末を持たない状態
  で =O_NOCTTY= 無しに開いた tty を制御端末にするため。
- macOS (XNU) の =bsd/kern/tty.c= =ttyopen= はセッションに触れず、制御
  端末の付与は =TIOCSCTTY= だけが行う。=bsd/kern/tty_tty.c=
  =cttyopen= は制御端末が無ければ =ENXIO= を返し、その strerror が
  "Device not configured"。
- POSIX.1-2024 Shell Command Language 2.7: 複数のリダイレクトは先頭か
  ら順に評価される。=</dev/tty 2>/dev/null= の順では open の失敗
  メッセージがまだ pty である fd 2 に出る。同 2.8.1 により、特殊組み込
  みでないコマンドのリダイレクト失敗はシェルを終了させないので、
  =stty= だけが飛ばされて =exec= には進む。

Linux でも =setsid= で制御端末を落とせば同じ症状を再現でき、修正で
消えることを確認した (上記 ERT がその再現)。

採らなかった案:

- 入力側も pty にして =TIOCSCTTY= を得る案は、spectreshell が子への
  入力を =process-send-string= だけで賄う設計 (=--force-pty-output=)
  を崩すため採らない。
- =/dev/tty= を残して stderr の捨て場だけ前に出す案は、エラー混入は
  消えるが macOS の階段状が残る。
- =/dev/tty= を試して失敗したら fd 1、という二段構えは、fd 1 だけで
  足りる以上ラッパを複雑にするだけ。
- =stty -F= / =-f= でデバイスを直接指定する案は、GNU と BSD で
  オプション名が違うため採らない。
- ラッパを捨てて Zig 側から slave を開いて =tcsetattr= する案は、
  =/bin/sh= と =stty= への依存は消えるが、子の最初の ioctl より前に
  サイズを与えるという現在の保証が失われる。将来 =stty= 非依存化が
  必要になったときの候補として記録しておく。
